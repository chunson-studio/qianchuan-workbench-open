# 不懂技术也能开始

把整个项目交给你正在用的 Agent，再发下面这句话：

```text
请开始部署。
```

接下来主要由 Agent 操作。只有登录、验证码、店铺选择，以及你自己的经营决定需要你参与。不要把登录凭据发到聊天里。

## 第一次需要做什么

1. **选项目。** 把项目文件夹作为 Agent 的当前项目打开。Agent 会核对记录保存的位置，不让你手填端口或内部路径。
2. **打开工作台。** Agent 检查环境并启动，给你一个本机页面地址。已有服务就直接使用。
3. **登录千川。** 在千川官方网站登录自己的账户。在 Codex 使用的本场浏览器完成登录，由 Codex 核验账户并接续，无需导出或粘贴 Cookie。
4. **核对店铺和计划。** 看名称，确认是不是你要看的那一家。多账户、多计划时，Agent 会列出名称供选择。
5. **需要罗盘时再接罗盘。** 在本场浏览器登录同一店铺的罗盘，由 Codex 核对直播间和场次后读取。暂时没有罗盘权限也可以先看已经取得的千川数据。
6. **看检查结果。** Agent 告诉你连好了什么、还缺什么。刚接好不等于已经开始定时盯盘，也不会默认替你改广告。

Cookie 是让本机读取账户数据的登录凭据。千川和罗盘登录态分别核验；过期时只重新登录失效的网站。未登录、没有罗盘数据和已经下播是不同情况，Agent 会核对后再说明。

浏览器登录、凭据保存位置及更新办法见[Cookie 获取与存放](#登录文件的获取与保存)。Agent 给出本机实际路径，用户不用猜文件名。

## 以后直接说这些话

工作台右上角的“隐私模式”适合演示或截图：开启后，账户名称显示为“账户 1、账户 2”，房间、计划、素材、订单及记录标识隐藏，ROI、消耗、目标、时间和状态照常显示。切换页面、刷新后会记住开关；再点一次恢复显示。它只改变页面展示，账户选择和实际请求仍绑定原来的对象。

| 你想做什么 | 发给 Agent 的话 |
|---|---|
| 今天继续用 | “读取日常接续指令，继续我的工作区。” |
| 看一眼现在的情况 | “帮我检查当前直播，只看一轮。” |
| 持续看本场 | “每5分钟帮我看一次，直到本场结束，有重要变化再告诉我。” |
| 下播后看结果 | “我下播了，按内置复盘指令整理这一场。” |
| 暂停这个盯盘任务 | “停止本次盯盘。” |
| 换另一个店铺 | “这次看另一个店铺，请先确认账户。” |

完整可复制文本见[日常接续](../workspace/运行入口/日常接续.md)、[循环指令](../workspace/运行入口/loop指令.md)、[复盘指令](../workspace/运行入口/复盘指令.md)。示例的5分钟是你使用该提示词时选择的检查频率，可直接改成自己需要的频率。

## Agent 应该怎样和客户说话

每次只说一个当前步骤，不一次抛出整张问卷。例：“现在请在这个页面选择千川 JSON 文件。”完成后再讲下一步。

能从电脑和接口查到的信息，Agent 先查。确实缺客户决定时，说明为什么需要，再给容易理解的选项；客户说不知道就记下来，继续能做的部分。不要要求客户回答 Node.js、MCP、端口或接口名称。按下表补问当前缺项，并把答案记入客户自己的接续状态。

遇到问题，Agent 先说“哪里没好、我已经查了什么、现在需要你做哪一步”。不要把一长串英文错误当作交付结果。只有聊天、没有本地工具的客户端无法代装和自动盯盘，必须如实说明；不要按模型品牌承诺能力。

## 按场景补问缺项

| 场景 | 先由 Agent 做 | 仍缺信息时怎样问 |
|---|---|---|
| 项目位置不明 | 读宿主当前项目和已有索引 | “这次的记录放在刚打开的哪个项目里？” |
| 多个可用账户 | 列出真实账户名称 | “这次看哪家店？这里有 A 和 B。” |
| 多个主计划 | 查询真实候选及状态 | “这两条都在投，这次重点看哪一条？” |
| 登录失效 | 确定千川还是罗盘失效 | “千川登录过期了，请先重新登录千川，其他配置不用重填。” |
| 需要罗盘数据 | 检查是否已有可用凭据 | “还缺罗盘的补充数据。这次先看千川，还是现在接罗盘？” |
| 准备持续盯盘 | 读取客户已给的账户、频率和结束条件 | 只问缺项，例如“这次看到下播就结束，可以吗？” |
| 缺少判断线 | 查账户当前策略和本次要求 | “一条测试最多接受花多少钱还没出单？” |
| 操作范围不明 | 查已授权范围、实际权限和接口能力 | “你希望我只给建议，还是按你确认的规则直接操作？” |
| 复盘对象不明 | 先查任务绑定与场次列表 | “你要看今天下午这场，还是昨天晚上的那场？” |
| 调度能力缺失 | 查宿主真实可用工具 | “这里不能自动定时唤醒。我已完成本轮检查，后续需要换到支持定时的客户端。” |

表中名称是示意，提问时必须替换为真实候选。不是每次都问这些问题，只问当前工作缺少的项。

账户接入时，问题以 setup_account status 的 next_questions 为准，保存使用当前 revision 和真实 Schema。目标、预算或停止线已经由客户说清楚时不重复问；表格里的表达方式不添加新必填字段。开户以外的目录、调度和复盘问题由对应流程检查，不受 next_questions 列表限制。

## 问完怎样继续

- 记录问题、已有答案、待答项和它影响的动作，换 Agent 后不要重新问一遍。
- 客户说“不知道”：记录待提供，不填 0、不填无限、不替他决定金额。
- 客户只想看数据：未知成本或 ROI 目标不应阻断已有数据展示。需要亏盈判断、额度或具体投放动作时，才补相应信息。
- 凭据只让本人在本机接入页导入。不让客户把 Cookie、密码、验证码或其他网站的数据发到聊天。
- 能修复的缺依赖、路径和本机配置问题由 Agent 修复并验证；权限弹窗、登录、验证码或必须本人决定的事项才交给客户。
- 写操作前已有明确授权且目标、参数和影响未改变时，不重复索要同一许可。新动作或新范围确需确认时，先准备具体方案。

## 对客户的每次汇报

先说结果，再给最多三项必要信息：
“已经连接好千川。现在可以看直播和计划数据；罗盘还没接。本次没有启动定时盯盘。”

失败时说明实际影响：
“这次千川请求失败，直播状态还不能确认。我没有把它当成下播，也没有修改计划。”

## 登录文件的获取与保存

当前使用 Codex 浏览器登录与接续，不再提供 Cookie Editor 文件选择或 JSON 粘贴入口。用户只需在本场浏览器完成千川登录，选择目标广告账户；需要罗盘时，再登录同一店铺的罗盘。Codex 核验账户、主计划、房间及开播时间后读取。

已有账户需要更新本机服务凭据时，Codex 按[已有账户凭据更新](../skills/qianchuan-ops/references/接入与执行.md#已有账户更新千川凭据)复用已验证脚本，核同广告户后同步并回读。首次新增账户仍须身份发现和接入核验；不能把已有账户刷新脚本称为自动开户。当前宿主没有凭据导出能力时记录准确缺口，不再要求用户安装扩展或手动导出文件。

罗盘优先在本场浏览器读取；当前千川凭据刷新脚本不支持罗盘同步，不能宣称两者已同时接入本机 API。暂时没有罗盘权限就记录缺口，继续可用的千川分析。

### 文件保存位置

由 Codex 在已授权范围内同步，程序负责校验与保存。全新部署默认以“千川工作台程序目录”为起点：

| 用途 | 默认位置 |
|---|---|
| Agent 本机同步的中间 JSON | private-runtime/credential-import/；不交给用户手动处理 |
| 千川实际读取文件 | private-runtime/scripts/qianchuan_cookie_<account_id>.txt；以 config.json 对应账户的 cookieFile 为准 |
| 罗盘实际读取文件 | private-runtime/scripts/compass_cookie_<account_id>.txt |
| 指定房间的罗盘文件 | private-runtime/scripts/compass_cookie_<account_id>_room_<room_id>.txt |
| 账户配置 | private-runtime/config.json |

旧安装可能仍使用 server-app/scripts/ 或其他目录。Agent 必须读取 setup 返回的 mcp.entry.env.QC_RUNTIME_CONFIG_ROOT，拼接 scripts/ 与该账户 cookieFile；罗盘房间读取优先使用同目录的房间文件，文件不存在才使用账户通用文件。任何文件都要先通过该房间的权限和开播时间核验；房间文件失效不改用其他店铺凭据重试。新场房间 ID 变化时需重新绑定，不凭店铺名称推断归属。不要一律告诉用户写 scripts/cookie.txt，不按店铺名猜 account_id。

部署时 Agent 把两份实际 Cookie 的**绝对路径**记入客户 workspace/部署检查.md，只记路径、是否存在、验证时间，不记内容。用户问“放哪个文件”，给出这次安装的准确路径和页面入口。

首次接入前还没有 account_id 和 cookieFile，由 Codex 核验浏览器身份并通过正式服务发现账户。内部 .txt 是 name=value; name=value 形式，与 JSON 不同；不能直接把 JSON 填入内部 .txt。首次接入也不能只创建 Cookie 文件而跳过身份核验。

### 失效后怎么办

只重新登录失效的网站，由 Codex 核验并处理必要的本机凭据同步。Agent 先核对官网是否能正常显示、账户是否选对、文件格式及错误码；HTTP 403 还可能与请求校验或网络有关，不能直接断言 Cookie 过期。

Cookie、导出 JSON、账户配置、Profile 和客户记录不进入公开 Git 或交付包。更新程序时保留这些本机资料。
